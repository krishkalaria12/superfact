Implementation plan · revision 2

Build the evidence before the answer.

A phased plan for an evidence-first Fact Diff engine that extracts atomic assertions from PDFs, keeps every assertion bound to the exact region it came from, and distinguishes corroboration, contradiction, and contextual reconciliation from cases it cannot safely decide.

Product promise

Upload documents. Receive precise claims with context and source evidence. See what agrees, what conflicts, what only appears to conflict, and what the system declined to judge.

A · North star

A small system whose behavior is clear.

The assignment states it plainly: a smaller, understandable prototype beats a large system whose behavior is unclear. So the system publishes fewer claims when necessary, never severs evidence from an assertion, and treats “cannot safely determine” as a valid result. The work is backend-heavy; the interface exists to make that behavior inspectable in seconds.

On accuracy claims

There is no labelled gold set and no measured accuracy figure anywhere in this plan. Building one over 511 pages would consume the schedule and still cover a single document family. Quality is instead pursued through mechanisms that hold without measurement: a deterministic verbatim-evidence gate, a context-completeness gate before publication, and a second adjudication pass reserved for contradictions.

Tuning happens by reading system output against the six starter PDFs. The README says exactly this under Limitations. An unmeasurable number in a submission is a question the reviewer will ask and the author cannot answer.

Definition of done

A new, unseen English PDF enters through the upload API and produces grounded assertions, context, evidence, and relationships with no document-specific rules, no hard-coded filenames, and no predicate allowlist. The supplied PDFs demonstrate corroboration, a likely contradiction, a contextual reconciliation, and one real failure the system handled honestly.

B · Architecture

One runtime, one coordinate space.

Revision 1 ran a Python parsing service on Modal and rendered evidence with PDF.js in the browser — two compute planes and two coordinate systems. MuPDF.js is the same C engine PyMuPDF wraps, compiled to WebAssembly and published to npm, so parsing collapses into the Next.js process. Because it also rasterizes pages, the highlight overlay reads the same coordinates the parser emitted.

Why the viewer renders images, not PDFs

The parser already produces a page raster and the bounding box of every line it read. Showing that raster with absolutely positioned highlight divs means the box drawn on screen is the box the parser emitted, scaled — no transform between two libraries’ conventions, which was the highest-ranked risk in revision 1. It also avoids shipping a 3 MB PDF to the client and parsing it there. The cost is losing text selection in the viewer, which an evidence inspector does not need.

C · Core contracts

Keep assertions immutable; let interpretations evolve.

The central modeling decision survives from revision 1: separate what a document said from the system’s interpretation of agreement or conflict. What changed is the surface area around it — five tables instead of thirteen, four verdicts instead of seven, and no entity-resolution tier. 

Assertion {
  documentId, page,
  subject, predicate, rawValue, canonicalValue, unit,
  qualifiers: JSONB,          // keys discovered per document, not fixed by schema
  modality: observed | projected,
  attributedTo: string | null, // set when the document credits another source
  evidence: { quote, bbox, lineIds },
  verified: boolean,           // quote found verbatim in the stored page text
  contextComplete: boolean,    // carries the qualifiers its predicate requires
  pipelineVersion
}
// Every document occurrence stays a separate immutable row, even when wording matches.

ClaimEdge {
  sourceAssertionId, targetAssertionId,
  verdict: corroborates | contradicts | reconciles | insufficient,
  reasonCode, matchedFields, mismatchedFields, explanation, confidence
}

// time_supersession, unit_mismatch, scope_mismatch, vintage_difference,

Implementation sequence

Build through vertical evidence slices.

Each phase exits with an inspectable artifact. A phase may begin when its stated dependency is stable. Eleven phases, and the two that carried the most weight in revision 1 — the parsing service and the evaluation harness — are gone entirely.

00Dependency: existing monorepo

Baseline and operating contract

Make the confirmed decisions executable without spending time on infrastructure the assignment does not judge.

Build

  • Wire the existing Turborepo workspaces: apps/web, packages/db, packages/env.
  • Define environment contracts for the model provider, Neon, Vercel Blob, and Inngest.
  • One local command runs Next.js and the Inngest dev server together.
  • Structured logs carrying job ID and stage name.

Freeze

  • English text-layer PDFs; reviewer-only deployment.
  • No auth, tenancy, retention workflow, or external tracing platform.
  • No Python service, Modal, Docling, OCR, Neo4j, Pinecone, or Mastra.
  • No accuracy metrics, benchmark datasets, or gold-set harness.
  • No hard-coded facts, filenames, predicates, or document-specific branches.
Exit checkA sample job moves through placeholder stages locally, with one job ID visible in both the database and the logs. Deployment is deliberately deferred to phase 10.
01Depends on 00

Domain model and contracts

Define the stable envelope that lets unfamiliar domains extend context without making comparisons meaningless.

Data model

  • Five tables: documents, pages, assertions, edges, jobs.
  • Fixed typed columns for identity, value, unit, modality, attribution, and evidence; JSONB for qualifiers.
  • Keep assertion occurrences separate even when wording and canonical value match.
  • Index document, page, subject, predicate, and job status; add the pgvector column on assertions.

Contracts

  • Zod schemas for parsed pages, assertion candidates, published assertions, edges, and the JSON export.
  • Stable reason codes rather than prose-only decisions.
  • Two publication states: published, or rejected with a reason.
  • A single pipelineVersion string stamped on every assertion.
Exit checkA hand-written assertion round-trips through storage and JSON export without losing raw value, canonical value, evidence, qualifiers, modality, or attribution.
02Depends on 01

Upload and durable job skeleton

Turn an uploaded file into an idempotent, progressive processing run.

Upload boundary

  • Accept PDFs through a route handler into Vercel Blob; persist key, URL, checksum, size, and original filename in Neon.
  • Hash content before expensive work and reuse completed artifacts for duplicate files.
  • Validate that the file opens; report encrypted or corrupted documents as explicit failures.
  • Detect a missing text layer and refuse the document with a clear scanned_unsupported reason rather than half-parsing it.

Job model

  • Emit an Inngest event after the document row commits.
  • Three stages: parse, extract, relate.
  • Make every stage safe to retry using job ID, content hash, and pipeline version.
  • Expose job status and per-page coverage through read-only endpoints.
Exit checkUploading the same file twice does not duplicate expensive work; retries do not duplicate assertions or edges; partial and failed states stay visible.
03Depends on 02

Parsing, table reconstruction, page rasters

Recover text, geometry, reading order, and table structure in one library, and produce the images the evidence viewer will highlight.

Structured text

  • Open each PDF with MuPDF.js; take toStructuredText per page for blocks, lines, and per-line bounding boxes.
  • Render each page with toPixmap().asPNG() at a fixed, recorded scale; store in Blob beside the page row.
  • Persist page text, line geometry, and the raster reference; record page quality signals (text density, replacement characters, image ratio).
  • Failed pages mark themselves failed without erasing successful ones.

Table reconstruction

  • Split each page into column bands by horizontal gap before clustering rows — two-column pages otherwise merge across the gutter.
  • Within a band, cluster lines into rows by y within tolerance, then order cells by x.
  • Read ruling lines through the onVector walker where a table is bordered; fall back to whitespace alignment where it is not.
  • Attach the governing table title, unit line, column headers, and footnotes to every cell before it can become an assertion.
  • Where a band resolves poorly, keep the page raster available for a vision read rather than emitting a malformed grid.
Exit checkThe RBI appendix tables and the Delhivery consolidated financial notes both reconstruct into rows whose cells retain title, unit, and column header. Highlight boxes drawn from stored geometry land correctly on the stored raster — verified by eye on one page before any later phase depends on it.
Observed during evaluation: on Delhivery’s notes pages the rupee glyph decodes as I, because the symbol is absent from the font’s encoding map. Currency must be inferred from the governing header line — “All amounts in Indian Rupees in million” sits on the same page — not from the character in the cell.
04Depends on 03

Atomic assertion extraction

Split prose and tables into independently testable propositions that carry the context needed to compare them.

Extraction pass

  • Batch lines by semantic section, preserving line IDs and page boundaries.
  • Use Luna with Structured Outputs to split compound prose into atomic assertions — this is the only stage that touches every page, so it carries the volume.
  • Extract subject, predicate, raw value, unit, qualifiers, modality, attribution, and the line IDs the claim rests on.
  • Build table assertions from title + row header + column header + cell + unit + footnote, never from an isolated number.

Qualifiers that follow the document

  • Let the model name its own qualifier keys and store them in JSONB — macro reports yield fiscal_year and geography, Delhivery yields segment and quarter.
  • Rank salience by numeric content and by repetition across documents; nothing more elaborate.
  • Treat document text as untrusted quoted data: it cannot rewrite instructions or change rules.
  • Retain low-confidence candidates internally rather than discarding them; the grounding gate decides what publishes.
Exit checkEvery candidate is atomic and points at line IDs that exist. The qualifier keys produced for the macro set visibly differ from those produced for the Delhivery set, with no schema change between runs.
05Depends on 04

Grounding gate and normalization

Stop structurally valid but unsupported model output from reaching the published tier, and make equivalent wording comparable without erasing what each document said.

Two hard gates

  • Verbatim: the quoted span must occur in the stored page text, and the cited lines must exist. Deterministic, no model involved, and the main defense against confident invention.
  • Context completeness: reject an assertion whose predicate demands a qualifier it lacks — a revenue figure with no period, a growth rate with no geography, a segment metric with no segment.
  • Check numbers, signs, percentages, currencies, dates, and units against the source span.
  • Rejections are stored with a reason and surfaced in the failures view; nothing is silently dropped.

Deterministic normalization

  • Normalize currencies, scales, percentages, units, signs, dates, fiscal periods, and ranges in code, never by model.
  • Keep the raw value beside the canonical value and record which rule converted it.
  • Represent time as an interval plus precision so FY, quarter, and calendar year stay comparable.
  • A handful of unit tests over these converters — the one place where testing is cheaper than inspection.
Exit check₹81,415.38 million and its canonical INR value remain traceably equivalent, with fiscal period and modality intact. No published assertion exists whose quote cannot be found in its page text.
06Depends on 05

Candidate pairing

Find every pair worth judging without an O(n²) sweep, and without asking similarity to decide truth.

Two retrieval paths

  • Deterministic: match on normalized predicate and comparable canonical value. Embeddings are unreliable on numbers — ₹7,225 crore against ₹72.25 billion is a coin flip in vector space and exact in this path.
  • Semantic: pgvector top-k over embedded subject and predicate text, catching the same fact worded differently.
  • Union and deduplicate the two. Full-text search is deliberately omitted; it overlaps both and earns its place only if pairs are visibly being missed.
  • Exact vector search at this scale; no HNSW index until something is actually slow.

Prefilter before any model call

  • A thousand-odd assertions at top-20 produces tens of thousands of pairs — far too many to adjudicate. The deterministic prefilter is what makes this phase tractable.
  • Drop pairs with incompatible value types or unrelated predicates before a model sees them.
  • Do not drop a pair merely because time, units, or scope differ — those differences are exactly what reconciliation explains.
  • Cap pairs per assertion and record what the cap excluded.
Exit checkKnown comparable pairs across the three Delhivery documents and the three macro documents reach the adjudicator. Semantically opposite but lexically similar claims arrive for judgement rather than being pre-labelled by similarity.
07Depends on 06

Relationship adjudication

Explain agreement and conflict at the level of entity, time, scope, unit, modality, and attribution — not as one opaque label.

Decision sequence

  • Apply deterministic equality, unit conversion, time-overlap, sign, and numeric tolerance checks first.
  • Send survivors to Terra with both evidence quotes and both qualifier sets bound to the prompt.
  • Never emit contradicts without evidence from both sides and a demonstration that the decisive context matches.
  • Where required context is missing on either side, return insufficient rather than guessing.

The contradiction second pass

  • Every pair Terra marks contradicts goes back through Terra high once more, with the burden reversed: argue why these are reconcilable.
  • Volume makes this affordable — contradictions are tens of pairs, not thousands — and contradiction precision is what the demo rests on.
  • Downgrade to reconciles when the second pass finds a decisive qualifier; keep both passes’ reasoning in the edge record.
  • Emit a concise comparison explanation, never raw chain-of-thought.
Exit checkThe system separates a genuine contradiction from a difference of time, data vintage, unit, scope, or projection-versus-actual, and shows which qualifier decided it.
Primary risk: attribution silently changes the proposition. “GDP will grow 6.5%” and “the RBI projects 6.5%” are not the same claim. Keep modality and attributedTo explicit in the prompt before any incompatibility is declared.
08Depends on 03–07

Speed, reuse, and incremental documents

Make the system feel fast by ordering work well and never repeating it, rather than by doing less of it.

Perceived latency

  • Map the whole document cheaply first, then process summaries, highlights, and table-dense pages ahead of body prose.
  • Stream verified facts to the UI as they land instead of waiting for the run to finish — this, not raw throughput, is what reads as fast.
  • Fan out page batches with bounded concurrency to respect provider and database limits.
  • Record stage timings, retries, and failure codes in logs for debugging.

Reuse

  • Skip parse and extraction entirely when a content hash has already been processed at the current pipeline version.
  • When a new PDF arrives, extract only its assertions and pair them against existing ones; never rebuild prior documents.
  • Recompute broadly only when the pipeline version changes.
  • Cache page rasters and embeddings alongside their source rows.
Exit checkFacts appear progressively while later pages are still processing. Re-uploading a processed PDF returns almost immediately. Adding a fourth document to a set does not reprocess the first three.
09Depends on 02, 05, 07

Inspection workspace

Make correctness reviewable in seconds without turning the assignment into a UI project.

Essential interface

  • Upload area and a job progress rail showing per-page coverage.
  • Ranked published facts with subject, predicate, raw and canonical value, qualifiers, modality, and attribution.
  • Filters for corroborated, contradictory, reconciled, insufficient, and failed.
  • Side-by-side relationship inspector and a JSON export button.

Evidence and failures

  • Render the stored page image and draw the assertion’s bounding box over it at the recorded scale.
  • For table facts, show the governing title, headers, cell, and footnote alongside the highlight.
  • A dedicated failures view: refused documents, failed pages, and rejected assertions with their reason codes.
  • Show denied contradictions with the qualifier that defused them — the most persuasive screen in the product.
Exit checkA reviewer selects any fact or relationship and reaches both exact evidence regions and the decisive context without reading logs. The failures view is populated with real failures, not empty.
10Depends on 07–09

Four cases, deployment, and handoff

Package the system so the company can understand the idea, run it, and verify the four required cases.

Demo cases

  • Identify candidate examples in the starter PDFs by hand early — revenue across the three Delhivery documents, GDP and inflation across Survey, RBI, and IMF, a director active in one filing and resigned in a later one — then build generically toward surfacing them.
  • Select every shown example from system output; hard-code no value, filename, predicate, or label.
  • Show one corroboration expressed differently in each source, one defensible contradiction with both evidence spans, and one denied contradiction reconciled by time, scope, unit, or vintage.
  • Show one real failure, the abstention behavior around it, and the repair path.

Submission

  • Deploy Next.js on Vercel with jobs through Inngest, data on Neon, files on Blob.
  • Commit a samples/ folder of exported JSON and page images so reviewers can evaluate without paid credentials.
  • Record a demo under three minutes: upload, progressive processing, facts and evidence, the four cases, one architecture trade-off.
  • README covering setup, approach, AI tools used, limitations — including the absence of measured accuracy — and next steps, over meaningful git history.
Exit checkA clean reviewer path succeeds from README to hosted demo or local run, and all four cases are inspectable directly from system-produced evidence.

Retired from revision 1

“Evidence points to the wrong visual region” was the highest-ranked risk. It is gone rather than mitigated: the parser and the viewer now share one coordinate space, so there is no transform left to get wrong.

Stop conditions

Do not add chat, graph visualization, a second parser, an accuracy harness, or decorative UI while any of the following is still true: published facts carry quotes that cannot be found in their page, contradictions survive that a qualifier would defuse, known pairs never reach the adjudicator, or the failures view is empty because failures are being swallowed.

What changed from revision 1

Removed: the Modal parsing service, Python, PyMuPDF, Docling, OCR, dual-parse comparison, chart vision extraction, UploadThing, derived facts, claim clusters, the entity and alias tables, the versioned predicate registry, browser PDF.js, open-ended risk-based model escalation, and every accuracy target, benchmark dataset, gold set, and evaluation phase. Thirteen tables became five, seven verdicts became four, five modality values became two plus an attribution field, and thirteen phases became eleven.

Added: MuPDF.js as a single in-process parser, coordinate-clustered table reconstruction with column-band splitting, page rasters as the evidence surface, a context-completeness gate at extraction, document-driven JSONB qualifier keys, the reversed-burden contradiction second pass, and a failures view in the UI.

Accepted decisions

Job-based processing; Vercel Blob; Vercel + Inngest; Neon with pgvector; AI SDK model layer in TypeScript; immutable assertions; deterministic normalization; MuPDF.js parsing and rasterization; precision over recall over latency; minimal UI; supplied-PDF demo; no measured accuracy claims.

Intentionally deferred

Authentication, tenancy, retention, abuse controls, multilingual support, scanned documents, chart data extraction, separate vector infrastructure, graph database, chat, and graph visualization. None is a prerequisite for a reviewer-only submission.
